# مستند ۴ — SECURITY (امنیت کلی سامانه)

## هدف
تعریف حداقل‌های امنیتی ثابت برای رمز، نشست، API، دیتابیس و فرانت‌اند.

## روش پیاده‌سازی (فایل‌ها)
`src/utils/password.js` (سیاست رمز)، `src/utils/crypto.js` (bcrypt 12 + بازهش)، `src/utils/totp.js` (2FA)، `src/utils/secret.js` (AES-256-GCM)، `src/routes/admin.routes.js` (`/admin/password`، `/admin/2fa/*`، `/admin/security`)، پنل ادمین → صفحهٔ «امنیت».

### چرا شمارهٔ موبایل در ستون رمز نشده؟
موبایل ستون `UNIQUE` است و با آن جست‌وجو/ورود انجام می‌شود. رمزنگاری ساده ستون را برای جست‌وجو بی‌فایده می‌کند؛ راه درست «رمزنگاری + ایندکس کورِ HMAC» است که تقریباً هر نقطه‌ای که موبایل می‌خواند/می‌نویسد را عوض می‌کند و **بدون دیتابیس واقعی نمی‌توانستم ایمن تستش کنم** (خطا یعنی هیچ‌کس نتواند وارد شود). تا آن موقع پیشنهاد می‌شود: رمزنگاری دیسک/Volume سرور (LUKS یا رمزنگاری دیسک ابر)، دسترسی شبکه‌ای محدود به Postgres، و پشتیبان رمز‌شده. در صورت تأیید شما، مرحلهٔ بعد را روی staging با دیتابیس واقعی انجام می‌دهیم.

### پشتیبان رمزنگاری‌شده (نمونهٔ دستور — تست‌نشده)
```bash
# روی سرور، با cron روزانه
docker exec sabegheno_db pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" \
 | gzip | gpg --symmetric --cipher-algo AES256 --batch --passphrase-file /root/.backup-pass \
 > /backups/sabegheno-$(date +%F).sql.gz.gpg
find /backups -name '*.gpg' -mtime +30 -delete   # با قانون ۳۰ روزهٔ DATA هماهنگ
```
حتماً **بازیابی** را هم یک‌بار روی سرور آزمایشی تمرین کنید.
